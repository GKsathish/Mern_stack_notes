====================================================================== 1.
HOW TO ANSWER SCENARIO-BASED INTERVIEW QUESTIONS
======================================================================

Use this structure for almost every scenario:

1.  Clarify the problem: Explain what the user sees and what the
    expected behavior should be.

2.  Identify possible causes: Separate frontend, backend, database,
    third-party service and infrastructure causes.

3.  Explain the investigation: Mention browser Network tab, React
    Profiler, API logs, database explain plans, server metrics or
    gateway transaction references as relevant.

4.  Explain the solution: Describe the exact frontend, backend and
    database changes.

5.  Explain failure handling: Include timeout, retry, duplicate request
    prevention, logging and recovery.

6.  Explain consistency and security: State which system is the source
    of truth and where validation happens.

7.  Explain verification: Mention unit tests, integration tests, load
    tests, monitoring and measurable results.

Example short interview structure: “First I would reproduce the issue
and identify which layer is responsible. I would check the browser
network request and backend logs, then inspect the database query or
external API response. After identifying the root cause, I would
implement the fix at the correct layer, add failure handling and tests,
and monitor the result in production.”

2. REACT PERFORMANCE AND LOADING OPTIMIZATION
======================================================================

Q1. Your dashboard takes 4.5 seconds to load. How would you reduce the
loading time?

INTERVIEW ANSWER: “First, I would measure the loading process instead of
immediately changing code. I would use Chrome DevTools Network and
Performance tabs, Lighthouse and React Profiler. I would identify
whether the delay comes from JavaScript bundle size, API response time,
database queries, images or unnecessary React rendering.

Then I would optimize the actual bottleneck: - Use route-level code
splitting and lazy loading for modules not needed initially. - Reduce
bundle size and remove unused dependencies. - Load critical dashboard
data first and non-critical widgets afterward. - Avoid duplicate API
calls. - Add pagination for large tables. - Optimize expensive
components and selectors. - Compress and appropriately size images. -
Use caching for data that does not change frequently. - Add skeleton
loaders to improve perceived loading experience.

After implementation, I would measure the same user flow under the same
test conditions and compare the results.”

EXAMPLE: const Reports = React.lazy(() => import(“./Reports”));

function Dashboard() { return ( <React.Suspense fallback={

Loading reports…

}> </React.Suspense> ); }

EXPLANATION: The Reports bundle is loaded when the component is rendered
instead of being included in the initial JavaScript bundle. Use an
appropriate route or component boundary so that the initial dashboard
does not wait for non-critical modules.

FOLLOW-UP QUESTIONS: - How did you measure 4.5 seconds? - Was it initial
page load, API response time or time to interactive? - Which components
were lazy-loaded? - How did you confirm that the change improved
performance? - Did you optimize backend APIs as well?

Q2. A page makes 100 API calls. How would you optimize it?

INTERVIEW ANSWER: “First I would inspect why 100 calls are being made. I
would group them into critical, dependent and non-critical requests.

For independent requests that are genuinely required together, I can use
Promise.all. For dependent requests, I will execute them in sequence. I
would also consider creating a backend aggregation endpoint if multiple
frontend calls are fetching related data and the backend can safely
combine them.

I would avoid firing every request at once. I would use batching or a
concurrency limit, caching, pagination and lazy loading. I would cancel
outdated search requests and avoid duplicate requests.”

EXAMPLE: const [users, transactions, statistics] = await Promise.all([
getUsers(), getTransactions(), getStatistics()]);

IMPORTANT: Promise.all rejects when one promise rejects. If independent
results should be handled separately, consider Promise.allSettled and
show partial results. Do not call 100 APIs concurrently just because
Promise.all is available.

Q3. A parent state change causes many child components to render. How
would you fix it?

INTERVIEW ANSWER: “I would first use React DevTools Profiler to identify
which components render and why. A render is not automatically a
performance problem, so I would focus on expensive or frequent
unnecessary renders.

I would keep state close to the component that needs it, split large
components, use React.memo for suitable child components, useMemo for
expensive calculations and useCallback when stable function references
are useful. I would also inspect Redux selectors and avoid selecting a
large object when a component needs only one small field.”

EXAMPLE: const UserCard = React.memo(function UserCard({ user }) {
return

{user.name}

; });

const filteredUsers = useMemo(() => { return users.filter(user =>
user.name.includes(search)); }, [users, search]);

const handleSelect = useCallback((id) => { setSelectedId(id); }, []);

IMPORTANT: - React.memo compares props by shallow comparison by
default. - Creating a new object or array on every parent render can
defeat memoization. - useMemo and useCallback have their own cost. Do
not add them everywhere. - State updates inside a component still cause
that component to render.

Q4. A dashboard contains 10,000 transaction rows. How would you display
them?

INTERVIEW ANSWER: “I would not load and render all 10,000 rows at once.
I would use server-side pagination so the backend returns only the
required page. I would support server-side filtering and sorting. If the
UI needs a long scrolling list, I would use virtualization so only
visible rows are mounted in the DOM.

For millions of records, I would use cursor-based pagination rather than
a very large skip value.”

KEY DIFFERENCE: Pagination limits the records fetched for a page.
Virtualization limits how many rows are rendered in the DOM. They can be
used together.

Q5. Explain React.memo, useMemo and useCallback.

React.memo: A higher-order component that can skip rendering a component
when its props have not changed according to its comparison.

useMemo: Caches the result of a calculation between renders while
dependencies remain unchanged.

useCallback: Caches a function reference between renders while
dependencies remain unchanged.

Example use cases: - React.memo: expensive transaction row component. -
useMemo: calculating filtered or grouped records. - useCallback:
callback passed to a memoized child component.

Q6. How do lazy loading and code splitting work?

INTERVIEW ANSWER: “Code splitting divides the JavaScript bundle into
smaller chunks. Lazy loading loads a chunk when the corresponding
component or route is needed. In React, React.lazy and Suspense provide
a common way to lazy-load components.”

EXAMPLE: const Analytics = React.lazy(() => import(“./Analytics”));

function AnalyticsPage() { return ( Loading analytics…
}> ); }

Q7. How would you optimize the initial screen?

ANSWER: - Load only the JavaScript needed for the initial route. - Fetch
critical data first. - Defer non-critical widgets. - Optimize images and
fonts. - Avoid duplicate requests. - Use caching where appropriate. -
Reduce expensive initial calculations. - Measure Core Web Vitals and
actual user performance.

Q8. An API takes 10 seconds. How would you handle the UI?

ANSWER: “I would show a loading or skeleton state and configure a
reasonable request timeout. If the request fails, I would show a clear
error and retry option. For a long-running operation, I would use
polling or WebSocket status updates. I would not assume that a timeout
means the backend operation did not happen.”

EXAMPLE WITH AXIOS: const response = await axios.get(“/api/users”, {
timeout: 10000, signal: controller.signal });

For payment or other write operations, verify operation status before
retrying.

Q9. How would you implement skeleton loading?

ANSWER: “I would create reusable skeleton components that match the
approximate shape of the actual content. While the API is loading, I
display the skeleton. When data arrives, I replace it with the real
content. If the request fails, I show an error state rather than leaving
the skeleton indefinitely.”

A good UI should handle loading, success, empty and error states.

Q10. The app is slow on mobile but fast on desktop. How would you
investigate?

ANSWER: “I would reproduce it using mobile device testing and network
throttling. I would inspect JavaScript execution, bundle size, image
size, API latency, layout shifts and expensive rendering. I would test
on an actual device too, because desktop emulation does not reproduce
every mobile limitation.”

Q11. Search triggers an API request on every keystroke. How would you
optimize it?

ANSWER: “I would debounce the input so the API is called after the user
pauses typing. I would cancel the previous request or ignore stale
responses so an older response cannot overwrite a newer search result.”

Example: - User types “mob”. - Requests should not necessarily be sent
for “m”, “mo” and “mob” immediately. - After a short pause, send the
search request for “mob”.

Q12. How do you prevent an older API response from overwriting a newer
result?

ANSWER: Use AbortController or request identifiers. Cancel the previous
request when the search term changes, or compare request IDs before
updating state.

Q13. How do you handle a dashboard with independent widgets?

ANSWER: I would separate widgets into components and API
responsibilities. Critical widgets can load first. Other widgets can
load independently and show their own loading and error states. One
failed chart should not necessarily prevent the whole dashboard from
rendering.

Q14. How do you optimize Redux state?

ANSWER: - Keep state normalized where appropriate. - Select only the
fields a component needs. - Use memoized selectors for expensive derived
data. - Avoid storing duplicate copies of the same server data. - Keep
local UI state local when it does not need to be shared. - Avoid
dispatching excessive updates for high-frequency events.

Q15. How do you measure whether an optimization worked?

ANSWER: I would compare before and after measurements under similar
conditions: initial load, Largest Contentful Paint, API duration, bundle
size, render duration and error rate. I would use browser tools and
production monitoring. I would not claim an improvement based only on
subjective observation.

3. REACT UI ARCHITECTURE AND USER FLOWS
======================================================================

Q1. How would you structure a large admin dashboard?

INTERVIEW ANSWER: “I would use a feature-based structure. Common layout
and UI components would be shared, while each feature would own its
components, API service, state and types. This makes the application
easier to maintain and allows teams to work on separate modules.”

SAMPLE STRUCTURE: src/ app/ store.ts router.tsx components/ common/
layout/ features/ users/ components/ usersApi.ts usersSlice.ts types.ts
transactions/ components/ transactionsApi.ts transactionsSlice.ts
wallet/ analytics/ reports/ hooks/ services/ utils/ types/

Q2. How would you design a multi-step payment UI?

INTERVIEW ANSWER: “I would define clear steps such as service selection,
details, confirmation, payment processing and result. I would keep UI
step state in React or Redux depending on how widely it is shared. The
actual order and payment status must be stored on the backend, not
trusted from frontend state.

If the user refreshes the page, the frontend should fetch the existing
order and display the correct status.”

Example UI states: IDLE ORDER_CREATED PAYMENT_PROCESSING PAYMENT_PENDING
PAYMENT_SUCCESS PAYMENT_FAILED SERVICE_PROCESSING SERVICE_SUCCESS
SERVICE_FAILED

Q3. How do you handle refresh during payment?

ANSWER: “I would store an order reference on the backend and provide a
status endpoint. After refresh, the frontend reads the order reference
and fetches the latest status. It should not create a new payment merely
because the page refreshed.”

Q4. How do you design reusable components across multiple portals?

ANSWER: “I would identify common UI patterns such as buttons, inputs,
modals, loaders, tables, headers and payment status components. I would
build reusable components with clear props and shared styling.
Portal-specific differences would be handled through configuration,
themes or feature flags rather than duplicating the entire component.”

Q5. How do you handle different API response structures?

ANSWER: “I would keep API-specific response handling in the service or
adapter layer. Each portal adapter would convert its response into a
common frontend model. Components would consume the normalized model
rather than knowing the different provider response formats.”

Q6. How would you build a responsive dashboard?

ANSWER: “I would use a mobile-first approach with CSS Grid, Flexbox and
breakpoints. I would make navigation collapsible, tables responsive,
controls touch-friendly and charts fit the available width. I would test
desktop, tablet and mobile sizes, including real devices.”

4. PAYMENT GATEWAY AND TRANSACTION RELIABILITY
======================================================================

CORE PAYMENT FLOW: 1. User selects a product or service. 2. Frontend
sends an order request to the backend. 3. Backend validates the user,
amount and business rules. 4. Backend creates an order with a unique
order ID and Pending status. 5. Backend creates or initiates a gateway
payment attempt. 6. User completes payment on the gateway. 7. Gateway
sends a response and/or webhook. 8. Backend verifies the gateway
signature and transaction details. 9. Backend updates payment status.
10. Backend fulfills the service or product order. 11. Frontend fetches
or receives the final status. 12. Reconciliation handles unresolved
transactions.

IMPORTANT RULE: The frontend success page is not proof of payment. The
backend must verify the gateway result using the gateway’s documented
verification mechanism.

Q1. User clicks Pay Now but the gateway takes 30 seconds. What do you
do?

ANSWER: “I would prevent accidental repeated clicks in the UI, create an
order on the backend and show a processing state. I would configure
timeouts based on the gateway documentation. If the request times out, I
would not automatically mark it failed because the gateway may have
processed it. I would check the transaction status through a status API
or webhook. The frontend would show Pending until the backend confirms
the final result.”

Q2. Amount is deducted but the application shows Failed. How do you
resolve it?

ANSWER: “I would collect the order ID, internal transaction ID and
gateway reference. I would check the gateway status API and webhook
logs. A network timeout may have prevented our server from receiving the
success response. If the gateway confirms success, I would update our
record and continue fulfillment. If payment succeeded but service
fulfillment failed, I would retry fulfillment or follow the refund
process. I would not ask the user to pay again before checking the
original attempt.”

Q3. User clicks Pay Now multiple times. How do you prevent duplicate
payments?

FRONTEND: - Disable the button while the request is being submitted. -
Prevent repeated submission in the event handler. - Show the current
order state.

BACKEND: - Generate or accept a stable idempotency key for the business
operation. - Store the key with a unique database constraint. - Return
the existing operation result for a duplicate request. - Use the
gateway’s idempotency support where available. - Check the existing
order and payment attempt before creating another one.

IMPORTANT: A frontend loading flag alone is not sufficient. Two requests
can reach the backend from different tabs, devices or network retries.

Q4. Gateway sends the same webhook multiple times. What do you do?

ANSWER: “I would verify the webhook signature first. Then I would use
the gateway event ID or another documented unique event identifier to
detect duplicate delivery. I would store processed event IDs with a
unique index. Processing must be idempotent. If the same event arrives
again, I return an appropriate successful acknowledgement without
applying the business effect twice.”

Q5. Gateway says Success but MongoDB still says Pending. What do you do?

ANSWER: “I would verify the transaction with the gateway. Then I would
update the internal transaction using a conditional state transition. I
would record the gateway reference, verification result and timestamps.
If the database update fails, the webhook retry or reconciliation job
should recover it. I would make sure a late event cannot incorrectly
move a final state backward.”

Q6. How do you implement retry?

ANSWER: “I first inspect the previous attempt. If it is Success, I do
not create a new payment. If it is Pending or unknown, I verify its
status before retrying. If it is confirmed Failed, I may create a new
payment attempt under the same business order, using a new attempt ID. I
maintain the history of every attempt.”

Q7. How do you maintain transaction history?

ANSWER: “I keep transaction records separate from the user document
because transactions grow over time. I store user ID, order ID, internal
transaction ID, amount, currency, payment method, status, gateway
reference and timestamps. I index common search fields and retain an
audit trail of status changes.”

SAMPLE TRANSACTION: { userId: ObjectId(“…”), orderId: “ORD100”,
transactionId: “TXN100”, amount: 500, currency: “INR”, paymentMethod:
“UPI”, status: “PENDING”, gatewayReferenceId: null, createdAt: new
Date() }

Q8. How do you verify a payment response?

ANSWER: “I follow the gateway’s official server-side verification
method. This may include signature verification, webhook signature
verification or a server-to- server status API. I compare the order ID,
amount, currency, merchant account and gateway reference. I never trust
a client-supplied success flag.”

Q9. Backend crashes after successful payment. What happens?

ANSWER: “The gateway may retry the webhook depending on its delivery
policy. I would also maintain pending transactions and run a
reconciliation process. The reconciliation job checks unresolved
transactions against the gateway and updates the internal status safely.
The process must be idempotent so that recovery does not create
duplicate fulfillment.”

Q10. How do you handle uncertain payment status?

ANSWER: “I keep the transaction Pending or in an explicit
unknown/reconciliation state. I query the gateway and wait for the
webhook. I do not treat timeout as failure. I do not create a second
charge while the first attempt is unresolved unless the gateway and
business rules confirm it is safe.”

Q11. Payment succeeded but recharge failed. What do you do?

ANSWER: “I maintain separate paymentStatus and serviceStatus. Payment
can be Success while recharge is Pending or Failed. I retry the provider
operation only when it is safe and idempotent. If the service cannot be
delivered, I follow the refund or reversal workflow. The user should see
an accurate status.”

Q12. What is reconciliation?

ANSWER: “Reconciliation compares our internal payment records with the
gateway’s records. It identifies cases such as gateway success with
internal Pending, internal success with a mismatch, missing webhook
events or unresolved transactions. It can run periodically and produce
alerts or recovery actions.”

Q13. What is idempotency?

ANSWER: “Idempotency means repeating the same logical request does not
create additional business effects. For example, retrying a payment
creation request with the same idempotency key should return the
existing operation rather than charging the user again.”

Q14. What statuses would you use?

Possible payment statuses: CREATED PENDING SUCCESS FAILED CANCELLED
REFUND_PENDING REFUNDED RECONCILIATION_REQUIRED

Possible service statuses: NOT_STARTED PENDING PROCESSING SUCCESS FAILED
REFUND_REQUIRED

The exact statuses should match the gateway and business lifecycle.
Avoid using one status field to represent both payment and service
fulfillment.

Q15. What should be logged?

-   Internal order ID.
-   Internal transaction ID.
-   Gateway reference ID.
-   Provider name.
-   Event ID.
-   Request correlation ID.
-   Status transitions.
-   Verification outcome.
-   Error code and timestamp.

Do not log card numbers, CVV, passwords, access tokens or other
sensitive payment credentials.

5. GAMING DASHBOARD AND WEBSOCKET SCENARIOS
======================================================================

Q1. 10,000 users are playing simultaneously. How do you manage live
updates?

ANSWER: “I would use authenticated WebSocket connections and organize
subscriptions by game, room or user. A user receives only the events
needed for the current game or screen. Admins receive authorized
operational and analytics events.

For horizontal scaling, I would run multiple application instances and
use a shared adapter or message broker such as Redis where appropriate.
I would load-test concurrent connections, message frequency, payload
size, CPU, memory and network usage.”

IMPORTANT: 10,000 connections are not automatically supported just
because WebSockets are used. Capacity depends on infrastructure, message
rate, payload size, subscriptions and implementation.

Q2. WebSocket disconnects during an active game. How do you reconnect?

ANSWER: “I would configure automatic reconnection with bounded retries
and backoff. After reconnecting, the client reauthenticates and rejoins
the authorized rooms. It then fetches the latest authoritative game
state through REST API. If the backend supports event replay, the client
sends its last processed sequence number and requests missed events.
Otherwise, it uses a fresh snapshot.”

EXAMPLE: const socket = io(API_URL, { reconnection: true,
reconnectionAttempts: 10, reconnectionDelay: 1000, reconnectionDelayMax:
10000 });

Q3. How do you prevent duplicate WebSocket event processing?

ANSWER: “I include a unique event ID and sequence or version number in
events. The client tracks recently processed event IDs and ignores
duplicates. For important business operations, deduplication must also
happen on the backend. Frontend deduplication is only a UI protection
and cannot guarantee financial correctness.”

EVENT EXAMPLE: { eventId: “EVT100”, sequence: 105, event: “ROUND_END”,
roundId: “ROUND100”, data: { winner: “DRAGON” } }

Q4. Dashboard displays an outdated balance. How do you synchronize it?

ANSWER: “The backend database is the source of truth. The backend
validates and commits the wallet operation first. Only after the
successful update does it publish a balance event. The frontend updates
its Redux state from the authorized event. After reconnecting or
detecting a sequence gap, it fetches the latest balance from REST API.”

Q5. Dashboard receives 1,000 events per second. How do you optimize
React?

ANSWER: “I would separate reliable event processing from visual
rendering. I would not dispatch a full React state update for every
incoming event. I would batch UI updates, aggregate metrics on the
backend, update only affected state and use memoized selectors and
virtualized lists. The visual update frequency can be throttled based on
product requirements, but important financial and game events must not
be silently dropped.”

Q6. How do you manage socket connections across components?

ANSWER: “I would use a centralized socket service or context/provider.
It owns the connection lifecycle. Components subscribe to required
events and remove their listeners during cleanup. I would avoid creating
a new socket connection inside every component.”

EXAMPLE: let socket;

export function connectSocket(token) { if (!socket) { socket =
io(API_URL, { auth: { token } }); } return socket; }

export function disconnectSocket() { if (socket) { socket.disconnect();
socket = null; } }

Q7. How do you handle missed events?

ANSWER: “I would include sequence numbers or versions. After
reconnecting, the client sends the last processed sequence. If the
server retains events, it can replay the missing range. If replay is not
available or there is a large gap, the client fetches a fresh snapshot
and continues from its latest version.”

Q8. How do you show live results without page refresh?

ANSWER: “The backend emits an event after the authoritative result is
finalized and persisted. The frontend listens for the event and updates
the relevant Redux state. React re-renders the affected components. I
also fetch a snapshot when the page first opens or reconnects.”

Q9. What happens when the WebSocket server restarts?

ANSWER: “Clients disconnect and reconnect. They reauthenticate, rejoin
rooms and fetch the latest state. In-memory state should not be the only
source of important game information. Persisted state and a shared event
infrastructure are needed for reliable recovery across instances.”

Q10. How do you keep REST and WebSocket data consistent?

ANSWER: “REST provides the initial snapshot and a recovery mechanism.
WebSocket provides subsequent updates. I use event versions or sequence
numbers so older events cannot overwrite newer state. The backend
remains authoritative.”

Q11. A bet is submitted but the API times out. What do you do?

ANSWER: “I do not assume that timeout means the bet was rejected. I use
a unique bet request ID and query the backend for its status. The
backend checks whether the bet was accepted and recorded. A retry uses
the same idempotency identity so that the same logical bet is not placed
twice.”

Q12. How do you prevent bets after a round closes?

ANSWER: “The backend validates the round state and server-side cutoff
time at the moment of accepting the bet. The frontend can disable the
button for user experience, but backend validation is authoritative. I
also use a unique request ID and persist the accepted bet.”

Q13. How do you store game round history?

ANSWER: “I use separate collections for game rounds, bets, results and
wallet transactions because they have different access patterns and
growth rates. I index round ID, game type, user ID and timestamps
according to the queries. I preserve audit information for important
game and financial operations.”

Q14. Two withdrawal or betting operations update the same wallet. How do
you avoid incorrect balance?

ANSWER: “I use an atomic conditional balance update, such as
decrementing only when the available balance is sufficient. I check the
update result. If the operation affects multiple documents, I use a
MongoDB transaction where appropriate. I also create a ledger record
with a unique business reference so retries cannot duplicate the
financial effect.”

Q15. How do you show live payout statistics?

ANSWER: “I calculate statistics on the backend from authoritative
transaction and payout records. For high-volume data, I may maintain
pre-aggregated summaries or use a streaming analytics pipeline. The
dashboard receives authorized updates through WebSockets. I distinguish
real-time provisional figures from finalized financial reports.”

6. CONSUMER PORTALS AND THIRD-PARTY API INTEGRATIONS
======================================================================

Q1. How do you design a shared component library for four portals?

ANSWER: “I identify common UI patterns and build reusable components
with clear interfaces. Common buttons, inputs, tables, modals, loaders,
headers and payment status components are shared. Portal-specific
branding is handled through themes or configuration. Business logic is
kept outside generic presentation components.”

Q2. Different portals return different API response structures. What do
you do?

ANSWER: “I keep provider-specific response parsing inside service
adapters. Each adapter maps its provider response to a common
application model. Components consume the common model and do not depend
on provider-specific field names.”

Q3. How do you implement one payment flow across multiple portals?

ANSWER: “I create a shared payment UI and service flow, but the backend
remains responsible for creating orders, communicating with the gateway,
verifying responses and updating transactions. Portal configuration
supplies the service-specific information. I keep payment and service
fulfillment statuses separate.”

Q4. Explain a mobile recharge flow.

ANSWER: 1. User enters mobile number. 2. Frontend validates input. 3.
Backend or provider lookup identifies operator/circle if required. 4.
Frontend displays available plans. 5. User selects a plan. 6. Backend
creates an order. 7. User completes payment. 8. Backend verifies
payment. 9. Backend submits recharge request. 10. Provider response
updates recharge status. 11. Frontend displays final status and
transaction history.

Q5. Payment succeeds but recharge API fails. What do you do?

ANSWER: “I store payment and recharge status separately. I inspect the
provider response to determine whether the recharge was accepted,
rejected or is unknown. I retry only when safe and according to provider
rules. If the recharge cannot be completed, I follow the refund or
reversal process. A timeout is not automatically a confirmed failure.”

Q6. How do you handle loading and error states?

ANSWER: “I model loading, success, empty and error states separately.
For a multi-step flow, I may use a state machine or Redux Toolkit to
prevent invalid transitions. Each independent widget can have its own
loading and error state.”

Q7. How do you handle provider timeout and retry?

ANSWER: “I configure provider-specific timeouts and retry policies. I
retry transient errors with exponential backoff when the operation is
safe. For financial or recharge requests, I first query status or use
the provider’s idempotency mechanism. I log correlation IDs and provider
references.”

Q8. How do you prevent duplicate recharge requests?

ANSWER: “I disable repeated submission in the UI, generate a stable
request ID and enforce idempotency in the backend. I store the provider
request reference and check existing processing status before submitting
another recharge.”

Q9. How do you keep the UI consistent across four portals?

ANSWER: “I use a shared component library, design tokens and responsive
rules. Common components have consistent behavior. Theme configuration
handles branding differences. I test shared components in all portal
contexts.”

Q10. How do you support mobile and desktop?

ANSWER: “I use responsive layouts, mobile-first CSS, accessible
controls, flexible tables and appropriate breakpoints. I test actual
device widths and browsers. I avoid relying only on desktop emulation.”

7. NODE.JS AND EXPRESS PRODUCTION SCENARIOS
======================================================================

Q1. An API takes five seconds. How do you identify the bottleneck?

ANSWER: “I measure the time spent in each layer: request parsing,
application logic, database, external provider and response
serialization. I use request IDs and structured timing logs. I inspect
MongoDB explain plans, external API latency, event-loop delay and server
CPU/memory. Then I optimize the layer that is actually slow.”

Q2. Multiple users update the same wallet. How do you prevent race
conditions?

UNSAFE PATTERN: 1. Read balance. 2. Calculate new balance in JavaScript.
3. Save the entire document.

Two requests can read the same old balance and overwrite each other.

SAFER ATOMIC UPDATE: const result = await Wallet.updateOne( { userId,
balance: { $gte: amount } }, { $inc: { balance: -amount } } );

if (result.modifiedCount !== 1) { throw new Error(“Insufficient balance
or wallet not found”); }

For a complete financial operation, use a transaction to update the
wallet and insert the ledger entry together. Also use idempotency and
unique transaction references.

Q3. Node.js server crashes in production. How do you investigate?

ANSWER: “I first restore service using the established process manager
or deployment procedure. Then I inspect application logs, process
manager logs, system logs, memory, CPU, recent releases and database
connectivity. I look for out-of-memory errors, unhandled failures,
event-loop blocking and dependency outages. I fix the root cause and add
monitoring or tests to prevent recurrence.”

Q4. API receives 10,000 requests per second. How do you scale?

ANSWER: “I would first load-test and identify the bottleneck. Depending
on results, I would use horizontal Node.js instances behind a load
balancer, caching, database optimization, rate limiting, connection
pooling and queues for background work. I would use a shared store or
message broker where multiple instances need coordinated state or event
delivery.”

Q5. How do you implement rate limiting?

EXAMPLE: const rateLimit = require(“express-rate-limit”);

const limiter = rateLimit({ windowMs: 15 * 60 * 1000, limit: 100 });

app.use(“/api”, limiter);

ANSWER: “This basic example limits requests per client within a time
window. For a multi-instance production deployment, I would use a shared
store such as Redis. Login, OTP and sensitive operations may need
stricter, separate limits.”

Q6. How do you implement centralized error handling?

ANSWER: “I use a common error middleware after the routes. Controllers
pass errors to next(error), or use an async wrapper. The middleware maps
known errors to safe HTTP responses, logs the details and avoids
exposing internal stack traces in production.”

EXAMPLE: app.use((err, req, res, next) => { const statusCode =
err.statusCode || 500;

res.status(statusCode).json({ success: false, message: statusCode ===
500 ? “Internal Server Error” : err.message }); });

Q7. How do you prevent duplicate API requests?

ANSWER: “For search and read requests, I use debounce, cancellation and
request deduplication where appropriate. For write operations, I use
idempotency keys and database uniqueness constraints. The solution
depends on whether the request is safe to repeat.”

Q8. Explain Worker Threads, Cluster and Child Processes.

Worker Threads: Useful for CPU-intensive JavaScript tasks that would
otherwise block the main event loop. They can share memory through
supported mechanisms.

Cluster: Runs multiple Node.js processes that can handle requests across
CPU cores. Each process has its own memory.

Child Process: Starts a separate process, often to execute external
commands or scripts.

INTERVIEW EXAMPLE: - Worker Threads: heavy calculation or CPU-intensive
processing. - Cluster: multiple Node.js server processes. - Child
Process: running a system command or independent script.

Ordinary asynchronous database and network I/O does not normally require
Worker Threads.

Q9. How do you validate API input?

ANSWER: “I validate body, params and query values before business logic.
I use a validation library such as Joi or Zod. I validate types,
required fields, lengths, allowed values and business constraints. I do
not trust frontend validation alone.”

Q10. How do you secure Express APIs?

ANSWER: - Authenticate users. - Authorize roles and permissions. -
Validate and sanitize input. - Apply rate limiting. - Use HTTPS. -
Configure CORS deliberately. - Use secure cookie settings where
appropriate. - Hash passwords with a suitable password hashing
algorithm. - Protect against injection and unsafe query construction. -
Verify webhook signatures. - Avoid exposing secrets in logs or
responses.

Q11. How do you prevent Node.js event-loop blocking?

ANSWER: “I avoid long synchronous loops and expensive synchronous file
operations in request handlers. I profile event-loop delay and move
CPU-intensive work to Worker Threads or background processes. I break
large jobs into smaller tasks when appropriate.”

Q12. How do you handle background jobs?

ANSWER: “I move work that does not need to complete within the HTTP
request into a queue. The API records the job and returns an appropriate
response. A worker processes it, retries safe failures and records job
status. For example, reports, notifications or reconciliation can be
background jobs. Financial jobs still need idempotency.”

Q13. How do you handle graceful shutdown?

ANSWER: “When the process receives a shutdown signal, I stop accepting
new requests, allow in-flight requests to finish within a controlled
timeout, close WebSocket connections appropriately, stop workers and
close database connections. This avoids abruptly interrupting operations
during deployment.”

8. MONGODB AND FINANCIAL DATA DESIGN
======================================================================

Q1. Your application has one crore users. How do you design the user
collection?

ANSWER: “I keep user documents in one users collection. I do not create
one collection per user. I design fields and indexes based on query
patterns. I use pagination, efficient projections and connection
pooling. If scale, storage or workload requires it, I evaluate sharding
using a carefully chosen shard key. I also monitor query performance and
storage growth.”

Q2. A user’s transaction history grows continuously. Embed or reference?

ANSWER: “I prefer a separate transactions collection because transaction
history is unbounded and independently queried. Embedding all
transactions can cause document growth and reach MongoDB’s 16 MB
document limit. The transaction document references the user through
userId.”

Q3. How do you optimize a slow query?

ANSWER: “I inspect the query with explain(), check whether it performs a
collection scan, review indexes, project only required fields and reduce
unnecessary work. I verify that the compound index order supports the
filter and sort. I measure before and after.”

Q4. How do you design indexes for transaction search?

Example: db.transactions.createIndex({ userId: 1, createdAt: -1 });

db.transactions.createIndex( { transactionId: 1 }, { unique: true } );

ANSWER: “I build indexes around actual filters, sorting and uniqueness
requirements. A compound index can support a user-specific transaction
list sorted by date. I check explain() to confirm index usage. Indexes
improve reads but add storage and write overhead.”

Q5. How do you handle concurrent wallet updates?

ANSWER: “I use atomic conditional updates for a single-document balance
operation. If wallet balance and ledger records must change together, I
use a multi-document transaction. I use idempotency and unique
references to prevent repeated processing.”

Q6. How do you paginate millions of records?

SKIP/LIMIT: Useful for simpler pagination and smaller offsets, but large
skip values can become expensive.

CURSOR PAGINATION: Use a stable indexed sort field and a tie-breaker.
For example, use createdAt and _id in the cursor so records with
identical timestamps are handled correctly.

ANSWER: “For large transaction collections, I prefer cursor pagination
with indexed sort fields. The API returns the next cursor rather than
asking MongoDB to skip a very large number of documents.”

Q7. When do you use aggregation?

ANSWER: “I use aggregation for server-side filtering, grouping,
calculations, joining related collections and reporting. For example, I
can calculate successful transaction totals per day using $match, $group
and $sort. I place selective $match stages early where appropriate and
inspect the pipeline performance.”

Q8. How do you archive old transactions?

ANSWER: “I first confirm retention, audit and regulatory requirements. I
can move older records to an archive collection or archival storage,
while keeping the active collection optimized for common queries. I
verify that reports and audit searches can still access archived
records. I do not delete financial records merely to reduce collection
size.”

Q9. How do you prevent duplicate transactions?

ANSWER: “I use unique indexes on the relevant transaction reference or
idempotency key. The backend checks the logical operation and handles
duplicate-key errors safely. A preliminary find() alone is not
sufficient because two requests can both pass the check concurrently.”

Q10. How would you design a wallet?

WALLET: { userId: ObjectId(“…”), balance: 10000, currency: “INR” }

LEDGER: { userId: ObjectId(“…”), transactionId: “TXN100”, type:
“WITHDRAWAL”, amount: 1000, status: “SUCCESS”, createdAt: new Date() }

ANSWER: “The wallet stores the current balance for efficient balance
reads. The ledger stores the history of financial movements. I update
the balance and create the corresponding ledger entry in a transaction
where required. I use unique transaction references, atomic updates and
audit history. For a robust financial system, I also define how
reversals, refunds and failed operations affect the ledger.”

Q11. What is the difference between embedding and referencing?

Embedding: Store related data inside the same document. Useful when
related data is small, bounded and commonly read together.

Referencing: Store related records separately and link them through IDs.
Useful when data grows independently, is shared or has its own query
lifecycle.

Example: A user’s small profile preferences may be embedded. A user’s
large transaction history should generally be referenced.

Q12. What is the MongoDB document size limit?

ANSWER: MongoDB BSON documents have a maximum size of 16 MB. If an
embedded array can grow without bound, redesign it using a separate
collection, bounded arrays or another appropriate pattern. Do not solve
unbounded growth by creating a new collection for every user.

9. AUTHENTICATION, AUTHORIZATION AND SECURITY
======================================================================

Q1. What is the difference between authentication and authorization?

Authentication verifies who the user is. Authorization verifies what the
authenticated user is allowed to do.

Example: Login verifies credentials and establishes identity. RBAC
checks whether the user’s role is permitted to access a report.

Q2. How does JWT authentication work?

ANSWER: “After successful credential validation, the server issues a
signed access token and, where applicable, a refresh token. The client
sends the access token with protected requests or uses a secure cookie
strategy. The server verifies the token signature and claims. When the
access token expires, the client uses a valid refresh session to obtain
a new access token.”

Q3. Where should tokens be stored?

ANSWER: “For browser applications, I generally prefer secure, HttpOnly,
SameSite cookies for refresh-token sessions because JavaScript cannot
read HttpOnly cookies. Access-token storage strategy depends on the
application architecture. If cookies are used for authentication, I also
consider CSRF protections. I avoid storing long-lived sensitive tokens
in localStorage because scripts running through an XSS vulnerability can
access them.”

Q4. What happens when a refresh token is stolen?

ANSWER: “I would use refresh-token rotation, server-side session
tracking and revocation. On refresh, the old token is invalidated and a
new token is issued. Reuse detection can revoke the token family or
session. I would also support logout from individual devices and audit
suspicious activity.”

Q5. How do you implement RBAC?

ANSWER: “I store roles or permissions and check them in backend
middleware for each protected endpoint. The frontend uses permissions to
control navigation and button visibility, but backend authorization is
the actual security boundary.”

Q6. How do you protect an admin dashboard?

ANSWER: “Use strong authentication, role and permission checks, secure
sessions, input validation, rate limits and audit logs. Sensitive
actions should be checked server-side and recorded with actor, action,
target and timestamp.”

10. PRODUCTION DEPLOYMENT AND TROUBLESHOOTING
======================================================================

Q1. Application works locally but fails in production. What do you
check?

ANSWER: “I compare the local and production environments. I inspect
browser console and network requests, backend logs, environment
variables, API URLs, CORS, database connectivity, file permissions,
Nginx routing and SSL configuration. I reproduce the issue and identify
the failing layer before changing code.”

Q2. Nginx returns 502 Bad Gateway. What do you check?

ANSWER: “502 usually indicates Nginx could not obtain a valid response
from the upstream service. I check whether Node.js is running, whether
the upstream port is correct, whether the process crashed, and whether
Nginx can reach the backend. I inspect Nginx error logs and application
logs.”

USEFUL COMMANDS: pm2 status pm2 logs sudo nginx -t sudo systemctl status
nginx sudo tail -f /var/log/nginx/error.log

Q3. SSL certificate expires. What happens?

ANSWER: “Browsers may show a certificate warning or reject the HTTPS
connection. I monitor expiry, renew the certificate using the configured
certificate process, validate the certificate chain and reload Nginx
safely. I verify the HTTPS endpoint after renewal.”

Q4. How do you deploy without affecting users?

ANSWER: “I use a controlled deployment process. For example, I can
deploy a new version separately, run health checks and switch traffic to
it. Blue-green deployment keeps the previous version available for
rollback. I also ensure frontend and backend API compatibility.”

Q5. How do you inspect production logs?

COMMANDS: pm2 logs pm2 logs app-name sudo tail -f
/var/log/nginx/access.log sudo tail -f /var/log/nginx/error.log

ANSWER: “I use structured logs with request IDs, timestamps, endpoint,
status code, duration and error details. I correlate frontend requests,
backend logs and provider references. I do not log passwords, tokens or
sensitive payment data.”

Q6. How do you handle API failures in production?

ANSWER: “I identify whether the failure is internal, database-related or
from an external provider. I return a controlled response, log the
correlation ID, retry transient failures only when safe, and use circuit
breakers for unhealthy dependencies. For payment operations, I preserve
the pending state and reconcile uncertain results.”

Q7. MongoDB becomes unavailable. What do you do?

ANSWER: “I check database service health, connectivity, credentials,
network, replica-set state and database logs. The application should
fail gracefully and return a service-unavailable response where
appropriate. After recovery, I verify unresolved operations and
reconcile important transactions.”

Q8. How do you rollback a failed deployment?

ANSWER: “I keep the previous stable build available. If health checks or
monitoring show a problem, I switch traffic back to the previous
version. I verify service health and investigate the failed release.
Database changes should be backward-compatible where possible so
rollback does not corrupt data.”

Q9. How do you monitor production?

ANSWER: “I monitor request rate, error rate, latency, CPU, memory,
event-loop delay, database performance, WebSocket connections and
external provider failures. I configure alerts for meaningful thresholds
and use logs with correlation IDs to investigate incidents.”

11. END-TO-END SYSTEM DESIGN SCENARIOS

Q1. Design a payment and recharge portal.

REQUIREMENTS: - User can register and log in. - User enters mobile
number. - User selects a recharge plan. - User pays through a gateway. -
Backend submits recharge to provider. - User sees final status and
transaction history.

HIGH-LEVEL COMPONENTS: Frontend: React, TypeScript, routing, forms,
loading and status UI.

Backend: Express routes, authentication middleware, validation, order
service, payment service, provider adapter and transaction service.

Database: Users, orders, payment attempts, recharge transactions and
ledger records.

FLOW: 1. User selects a plan. 2. Frontend sends an order request. 3.
Backend validates user, plan and amount. 4. Backend creates an order. 5.
Backend initiates payment. 6. Gateway processes payment. 7. Backend
verifies payment. 8. Backend submits recharge. 9. Provider response
updates recharge status. 10. Frontend fetches or receives final status.

FAILURE CASES: - Payment timeout: keep Pending and verify. - Duplicate
request: idempotency. - Payment success, recharge failure: retry or
refund workflow. - Provider timeout: check provider status before
retry. - Backend crash: webhook retry and reconciliation.

Q2. Design a gaming admin dashboard.

REQUIREMENTS: - Admin login. - User management. - Game configuration. -
Transaction monitoring. - Wallet and payout reports. - Real-time player
activity. - Role-based permissions.

FRONTEND: React and TypeScript. Redux Toolkit for shared state. React
Router for routes. Axios for REST APIs. WebSocket for live updates. Lazy
loading for large modules.

BACKEND: Node.js and Express. JWT authentication. RBAC middleware. REST
APIs. WebSocket server. Validation and centralized errors.

DATABASE: Users. Roles and permissions. Wallets. Ledger transactions.
Game rounds. Bets. Payouts. Analytics summaries.

REAL-TIME FLOW: 1. Admin opens dashboard. 2. REST API fetches initial
snapshot. 3. WebSocket connection authenticates. 4. Admin subscribes to
authorized events. 5. Backend publishes updates after authoritative
changes. 6. Redux updates affected state. 7. Reconnection fetches a
fresh snapshot or missed events.

SCALABILITY: Use multiple backend instances, shared event delivery,
monitoring and load testing. Keep authoritative game and financial state
in durable backend storage, not only in browser memory.

Q3. Design a wallet system.

REQUIREMENTS: - Deposit. - Withdraw. - Balance. - Transaction history. -
Refund. - Audit.

IMPORTANT DESIGN: - Wallet stores current balance. - Ledger stores
financial movements. - Every operation has a unique business
reference. - Atomic updates prevent lost balance updates. - Transactions
keep related writes consistent. - Idempotency prevents duplicate
operations. - Reconciliation identifies unresolved external payments.

Q4. Design a real-time dashboard for 10,000 concurrent users.

ANSWER: “I would clarify the number of concurrent connections, event
rate, payload size, room distribution, latency target and recovery
requirements. I would then load-test the architecture. I would use
WebSocket gateways, multiple instances, shared pub/sub where required,
authenticated room subscriptions, backpressure and event batching for
UI. REST APIs provide snapshots and recovery. Monitoring covers
connections, event-loop delay, message rate, memory and dropped or
delayed events.”

Q5. A production incident affects payment and gaming balance. How do you
respond?

ANSWER: “First, I would follow incident procedures and limit further
impact. I would identify affected users and operations, preserve logs
and transaction references, and avoid manual balance changes without
audit. I would compare the authoritative ledger, wallet state and
provider records. I would reconcile affected operations, communicate
status through the appropriate team and verify recovery with tests and
monitoring. I would document root cause and preventive actions.”
