WEBSOCKET INTERVIEW PREPARATION 4+ YEARS EXPERIENCE – MERN STACK
DEVELOPER PROJECT CONTEXT: REAL-TIME SLOT GAME UI
============================================================

PURPOSE This document is designed for a developer with 4+ years of
React.js and MERN Stack experience. It focuses on interview-ready
technical explanations, real project scenarios, architecture, code
patterns, production concerns, and likely follow-up questions. All
explanations are in English.

  -----------------------
  1. WHAT IS WEBSOCKET?
  -----------------------

Technical definition: WebSocket is a communication protocol that
provides a persistent, full-duplex communication channel between a
client and a server over a single TCP connection. It begins with an HTTP
Upgrade handshake. After the handshake succeeds, both sides can send
messages independently without creating a new HTTP request for every
message.

Simple explanation: With normal HTTP, the client sends a request and the
server returns a response. With WebSocket, the connection remains open,
so the client and server can exchange messages whenever needed.

Slot game example: 1. The player clicks the Spin button. 2. The React
frontend sends a SPIN_REQUEST message. 3. The Node.js backend validates
the player, bet, and game state. 4. The backend determines the
authoritative game result. 5. The backend sends a SPIN_RESULT message.
6. React updates the reels, win amount, and displayed balance.

Interview answer: “I used WebSocket for real-time, bidirectional
communication between the slot game frontend and backend. The client
sends game actions such as spin requests, and the server sends results
and game-state updates through the established connection. This avoids
repeated polling and provides low-latency communication.”

  ----------------------
  2. HTTP VS WEBSOCKET
  ----------------------

HTTP: - Usually follows a request-response communication model. - The
client initiates each request. - A request normally receives a
response. - Suitable for REST APIs, login, profile, reports, and CRUD
operations.

WebSocket: - Maintains a persistent connection after the handshake. -
Supports full-duplex communication. - Both client and server can
initiate messages. - Suitable for live game updates, chat, live
notifications, and collaborative applications.

Slot game usage: - Use HTTP/REST for login, loading player profile, and
fetching game configuration. - Use WebSocket for spin requests, game
events, and real-time updates.

Interview question: Why not use HTTP polling? Answer: “Polling
repeatedly sends requests even when there is no new data. WebSocket
keeps a connection open and allows the server to push updates when
events occur. This reduces unnecessary repeated requests and is useful
for real-time applications.”

Important nuance: WebSocket is not automatically better for every API.
Normal REST APIs are simpler and appropriate for request-response
operations.

  ---------------------------
  3. WEBSOCKET VS SOCKET.IO
  ---------------------------

WebSocket: - A standard communication protocol. - Browser support is
available through the native WebSocket API. - Provides connection and
message primitives. - Does not automatically provide Socket.IO’s rooms,
namespaces, automatic reconnection, or event abstraction.

Socket.IO: - A library built for real-time bidirectional
communication. - Uses its own event protocol and can use WebSocket as a
transport. - Provides events, rooms, namespaces, reconnection support,
and broadcasting features. - A Socket.IO client is not directly
compatible with a plain WebSocket server.

Interview answer: “WebSocket is the protocol, whereas Socket.IO is a
real-time communication library that provides additional features such
as rooms, namespaces, event-based messaging, and reconnection. I would
choose based on the application requirements and existing architecture.”

  --------------------------------------
  4. HOW THE WEBSOCKET HANDSHAKE WORKS
  --------------------------------------

1.  The browser starts with an HTTP request containing Upgrade:
    websocket and Connection: Upgrade headers.
2.  The server validates the request and responds with HTTP 101
    Switching Protocols if it accepts the upgrade.
3.  The connection is now a WebSocket connection.
4.  Client and server exchange WebSocket frames over the same TCP
    connection.

Interview answer: “The WebSocket connection starts as an HTTP request.
The client asks the server to upgrade the connection using the Upgrade
header. If the server accepts, it responds with 101 Switching Protocols,
and further communication happens using the WebSocket protocol.”

  ------------------------------
  5. FULL-DUPLEX COMMUNICATION
  ------------------------------

Definition: Full-duplex communication means the client and server can
send data independently at the same time over the established
connection.

Slot game example: The client sends a spin request while the server can
independently send a balance update or a game-status event.

Compare: - Simplex: communication in one direction only. - Half-duplex:
both directions, but not simultaneously. - Full-duplex: both directions
can communicate independently.

  -----------------------------------
  6. WEBSOCKET CONNECTION LIFECYCLE
  -----------------------------------

Browser WebSocket readyState values: - CONNECTING (0): connection is
being established. - OPEN (1): connection is ready for communication. -
CLOSING (2): connection is closing. - CLOSED (3): connection is closed
or could not be established.

Important browser events: - open: connection established. - message:
data received. - error: an error occurred. - close: connection closed.

Example: const socket = new WebSocket(“ws://localhost:8080”);

socket.onopen = () => console.log(“Connected”); socket.onmessage =
(event) => console.log(event.data); socket.onerror = (error) =>
console.error(error); socket.onclose = () =>
console.log(“Disconnected”);

  --------------------
  7. WS:// VS WSS://
  --------------------

ws://: - WebSocket over an unencrypted connection. - Commonly used for
local development.

wss://: - WebSocket over TLS encryption. - Should be used in
production. - Protects communication in transit.

Production example: const socket = new
WebSocket(“wss://api.example.com/socket”);

Security note: A production application should validate the Origin,
authenticate connections, authorize each action, validate incoming
messages, and avoid exposing long-lived credentials in URLs.

  ------------------------------------------
  8. WHY USE useRef FOR A SOCKET IN REACT?
  ------------------------------------------

Interview answer: “I use useRef to store the WebSocket instance because
the socket is a mutable object that should persist across renders.
Updating a ref does not trigger a React re-render. I use state
separately for UI values such as connection status and incoming data.”

Example: const socketRef = useRef(null);

socketRef.current = new WebSocket(“wss://example.com/socket”);

Why not useState for the socket? A state update triggers a render. The
socket instance itself usually does not need to cause a render whenever
it is assigned or accessed.

  ------------------------------
  9. REACT WEBSOCKET LIFECYCLE
  ------------------------------

A common pattern: - Create the connection in useEffect. - Store the
instance in useRef. - Register open, message, error, and close
handlers. - Update React state when UI-visible data changes. - Close the
connection and clear timers during cleanup.

Example: useEffect(() => { const socket = new
WebSocket(“ws://localhost:8080”); socketRef.current = socket;

socket.onopen = () => setStatus(“connected”); socket.onmessage = (event)
=> { const message = JSON.parse(event.data); setLastMessage(message); };
socket.onclose = () => setStatus(“disconnected”);

return () => { socket.close(); socketRef.current = null; }; }, []);

Interview follow-up: What happens if a component unmounts? Answer: “The
cleanup function closes the connection and clears associated timers or
listeners. This prevents unnecessary connections and resource leaks. If
the connection is shared across multiple screens, I would manage it in a
shared service or context rather than opening a separate connection in
every component.”

  ------------------------------------------
  10. MESSAGE STRUCTURE AND EVENT HANDLING
  ------------------------------------------

Use a consistent message envelope: { “type”: “SPIN_REQUEST”, “payload”:
{ “requestId”: “unique-request-id”, “betAmount”: 10 } }

Possible server response: { “type”: “SPIN_RESULT”, “payload”: {
“requestId”: “unique-request-id”, “reels”: [2, 5, 2], “winAmount”: 50,
“balance”: 1040 } }

Common message types: - SPIN_REQUEST - SPIN_RESULT - SPIN_ERROR -
BALANCE_UPDATE - GAME_STATUS - PING - PONG

Why use a type field? “It allows the client to identify the event and
route it to the appropriate handler. It also makes the message contract
easier to extend and maintain.”

  ----------------------------
  11. AUTOMATIC RECONNECTION
  ----------------------------

Why is reconnection needed? A connection can close because of network
changes, server restarts, proxy timeouts, or temporary connectivity
issues.

Recommended approach: - Detect the close event. - Retry after a delay. -
Increase the delay after repeated failures (exponential backoff). - Add
random jitter to avoid many clients reconnecting together. - Stop
retrying when the user logs out or the component is disposed. - Reset
the retry counter after a successful connection.

Example backoff: const delay = Math.min(1000 * 2 ** attempt, 30000);
const jitter = Math.random() * 500;

Important: Do not blindly resend a financial or game action after
reconnecting. The server may already have processed it. Use request IDs
and server-side idempotency, then query the request status.

  ------------------------------
  12. HEARTBEAT: PING AND PONG
  ------------------------------

Purpose: A heartbeat helps detect connections that appear open locally
but are no longer responsive across the network.

There are two related mechanisms: 1. Application-level messages such as
{“type”:“PING”} and {“type”:“PONG”}. 2. WebSocket protocol-level ping
and pong control frames.

A robust server can periodically send protocol-level ping frames and
terminate clients that fail to respond with pong.

Interview answer: “I use heartbeat checks to detect stale or half-open
connections. The server periodically sends a ping and expects a pong. If
the client does not respond within the configured timeout, the server
can close the connection and release its resources.”

  ---------------------------------------
  13. NODE.JS WEBSOCKET SERVER USING ws
  ---------------------------------------

Install: npm install ws

Example: const WebSocket = require(“ws”);

const wss = new WebSocket.Server({ port: 8080 });

wss.on(“connection”, (socket) => { console.log(“Client connected”);

socket.send(JSON.stringify({ type: “WELCOME”, payload: { message:
“Connected” } }));

socket.on(“message”, (raw) => { let message;

    try {
      message = JSON.parse(raw.toString());
    } catch {
      socket.send(JSON.stringify({
        type: "ERROR",
        payload: { message: "Invalid JSON" }
      }));
      return;
    }

    if (message.type === "PING") {
      socket.send(JSON.stringify({ type: "PONG" }));
    }

});

socket.on(“close”, () => { console.log(“Client disconnected”); });

socket.on(“error”, (error) => { console.error(error); }); });

console.log(“WebSocket server running on port 8080”);

Note: This is a learning example. A production server also needs
authentication, authorization, validation, rate limiting, heartbeat,
logging, and graceful shutdown.

  ----------------------------------------
  14. INTEGRATING WEBSOCKET WITH EXPRESS
  ----------------------------------------

A WebSocket server can share the same HTTP server as Express.

Example: const express = require(“express”); const http =
require(“http”); const WebSocket = require(“ws”);

const app = express(); const server = http.createServer(app);

const wss = new WebSocket.Server({ server, path: “/ws” });

app.get(“/health”, (req, res) => { res.json({ status: “ok” }); });

wss.on(“connection”, (socket) => { socket.send(JSON.stringify({ type:
“CONNECTED” })); });

server.listen(8080, () => { console.log(“HTTP and WebSocket server
running on 8080”); });

Interview answer: “I create an HTTP server from the Express application
and attach the WebSocket server to that same server. This allows HTTP
routes and the WebSocket endpoint to run on the same port, while keeping
their communication responsibilities separate.”

  -------------------------------------
  15. SLOT GAME REQUEST-RESPONSE FLOW
  -------------------------------------

Frontend: 1. Player clicks Spin. 2. React checks that the socket is
OPEN. 3. React creates a unique requestId. 4. React sends SPIN_REQUEST
with the bet amount. 5. UI shows a pending state and prevents accidental
repeated clicks.

Backend: 1. Authenticate the connected user. 2. Validate the message
schema and bet limits. 3. Check the player’s current balance. 4. Check
whether requestId was already processed. 5. Process the spin using the
approved server-side game logic. 6. Persist the result and balance
atomically. 7. Send SPIN_RESULT with the requestId and authoritative
result.

Frontend: 1. Match the response using requestId. 2. Update the displayed
balance from the server response. 3. Animate the reels based on the
returned result. 4. Show the win or loss state.

Critical rule: The frontend must never decide the authoritative win
amount or balance. The server must validate and calculate the result.

  ------------------------------------------------
  16. DUPLICATE REQUEST PREVENTION / IDEMPOTENCY
  ------------------------------------------------

Problem: A client may retry a request after a timeout even though the
server already processed the original request. This can cause duplicate
processing if the backend is not protected.

Solution: - Generate a unique requestId for each spin. - Scope the
idempotency key to the authenticated user. - Store the request status
and result durably. - Enforce uniqueness in persistent storage. -
Process balance debit, result creation, and credit in a transaction
where supported. - Return the previously stored result for a repeated
requestId.

Interview answer: “I use an idempotency key for each spin request. The
backend checks whether that user and requestId have already been
processed. If so, it returns the stored result instead of processing the
spin again. For production, this must be backed by persistent storage
and transaction-safe balance updates, not just an in-memory Map.”

  ---------------------------------
  17. AUTHENTICATION AND SECURITY
  ---------------------------------

Important controls: - Authenticate the connection during the
handshake. - Prefer a short-lived, single-use WebSocket ticket obtained
through an authenticated HTTPS endpoint. - Validate the Origin header
where appropriate. - Authorize every message/action, not only the
initial connection. - Validate message type, payload shape, size, and
values. - Apply per-user and per-connection rate limits. - Use wss:// in
production. - Avoid logging secrets or sensitive payloads. - Close
abusive or invalid connections. - Do not trust client-provided balance,
payout, or game result.

Browser note: The native browser WebSocket constructor does not provide
a general way to set arbitrary custom request headers. A short-lived
ticket or secure cookie-based approach may be used depending on the
architecture.

  -----------------------------------------------
  18. BROADCASTING, ROOMS, AND MULTIPLE CLIENTS
  -----------------------------------------------

Broadcasting: Sending a message to all connected clients.

Rooms: A logical grouping of clients, for example players in the same
game table or tournament.

Namespaces: Separate communication channels for different application
features in Socket.IO.

With plain ws: You can maintain your own Map or Set of clients and
groups.

With Socket.IO: Rooms and broadcasting are built-in features.

Slot game example: A tournament leaderboard update may be broadcast to
all players in the tournament room. A private balance update must only
be sent to the authenticated player.

  -------------------------------
  19. SCALING WEBSOCKET SERVERS
  -------------------------------

Challenge: A persistent connection is attached to a particular server
instance. When the application runs across multiple Node.js instances,
one instance may not know about events received by another.

Common approach: - Run multiple WebSocket server instances. - Use a load
balancer configured for WebSocket upgrades. - Use sticky sessions if
required by the deployment and architecture. - Use Redis Pub/Sub or
another message broker to distribute events. - Keep authoritative game
and balance data in shared persistent storage. - Monitor active
connections, message rates, latency, and errors.

Interview answer: “To scale WebSocket connections, I can run multiple
Node.js instances behind a load balancer. A shared messaging layer such
as Redis Pub/Sub can distribute events between instances. Persistent
game state and balances should be stored centrally so that any instance
can work with the authoritative data.”

  ---------------------------------------------
  20. REDIS PUB/SUB IN REAL-TIME APPLICATIONS
  ---------------------------------------------

Redis Pub/Sub allows one process to publish a message to a channel and
other subscribed processes to receive it.

Example: - WebSocket server A receives a game event. - It publishes the
event to a Redis channel. - WebSocket server B receives the event. -
Server B forwards it to its connected clients.

Important limitation: Redis Pub/Sub is not a durable message queue. If a
subscriber is offline, it can miss messages. For events that must not be
lost, consider a durable queue or stream and persistent application
state.

  ----------------------------------------------
  21. ERROR HANDLING AND PRODUCTION MONITORING
  ----------------------------------------------

Handle: - Invalid JSON. - Unsupported message type. - Unauthorized
action. - Invalid or excessive bet. - Connection timeout. - Unexpected
disconnection. - Server overload. - Duplicate request. - Database
failure.

Monitor: - Active connections. - Connection attempts and failures. -
Reconnection frequency. - Message throughput. - Message processing
latency. - Error rates. - Event loop delay. - Memory usage. - Heartbeat
timeouts.

Do not log authentication tokens, passwords, or sensitive player data.

  22. COMMON 4+ YEARS INTERVIEW QUESTIONS AND ANSWERS
  -----------------------------------------------------

Q1. Why did you use WebSocket in your slot game? A: “The game required
real-time bidirectional communication. WebSocket allowed the frontend to
send player actions and receive server events over a persistent
connection without repeatedly polling REST APIs.”

Q2. What is the difference between WebSocket and HTTP? A: “HTTP
generally follows a request-response model, while WebSocket provides a
persistent full-duplex channel. I use REST for normal resource
operations and WebSocket for real-time events.”

Q3. What happens if the connection disconnects during a spin? A: “The
client marks the connection as disconnected and attempts to reconnect
with backoff. It does not blindly submit the spin again. After
reconnecting, it queries the status using the original requestId so it
can determine whether the server processed the spin.”

Q4. How do you prevent duplicate spin requests? A: “I generate a unique
requestId for every spin. The backend enforces idempotency for the
authenticated user and returns the stored result if the same request is
received again.”

Q5. Why use useRef for the WebSocket instance? A: “The socket is a
mutable object that needs to persist between renders. useRef stores it
without causing re-renders. I use React state for values that must
update the UI, such as connection status.”

Q6. How do you detect a dead connection? A: “I use heartbeat checks. The
server periodically sends protocol-level ping frames and expects pong
responses. If a client fails to respond within the timeout, the server
terminates the stale connection.”

Q7. How do you secure WebSocket communication? A: “I use TLS through
wss://, authenticate the connection, validate the Origin, authorize each
action, validate incoming payloads, apply rate limits, and never trust
client-provided balance or payout values.”

Q8. How do you scale WebSocket connections? A: “I deploy multiple
Node.js instances behind a WebSocket-capable load balancer and use a
shared messaging layer such as Redis Pub/Sub to distribute events
between instances. Persistent application state is stored centrally.”

Q9. Can WebSocket work with Express? A: “Yes. I create an HTTP server
using the Express app and attach a WebSocket server to it. HTTP routes
and WebSocket communication can then share the same underlying server.”

Q10. Is Socket.IO the same as WebSocket? A: “No. WebSocket is a
protocol. Socket.IO is a library that provides event-based communication
and additional features such as rooms, namespaces, and reconnection.
They are not wire-protocol compatible.”

Q11. Should the frontend calculate the win amount? A: “No. The backend
must be authoritative. The frontend displays the result received from
the server. This prevents clients from manipulating payouts or
balances.”

Q12. What is backpressure? A: “Backpressure occurs when data is produced
faster than the receiver can process it. The application should control
message rates, queue sizes, and payload sizes, and avoid unbounded
buffering.”
