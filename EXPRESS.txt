DAY 1: EXPRESS FUNDAMENTALS
====================================================================

1. WHAT IS EXPRESS.JS?

Definition:
"Express.js is a fast, lightweight, and minimal web application framework built on top of Node.js. It simplifies backend development by providing features such as routing, middleware, request-response handling, and REST API development."

Example:
const express = require("express");
const app = express();

app.get("/", (req, res) => {
  res.json({ message: "Server running" });
});

app.listen(5000);

Use case:
REST APIs, admin dashboards, authentication services, microservices.

Internal working:
Express wraps Node.js HTTP server. It registers routes and middleware. When request arrives, Express matches route and executes middleware chain before sending response.

Follow-up questions:
1. Is Express mandatory for Node.js?
2. What is middleware?
3. How does Express handle routing?
4. What is Express application object?

Interview-ready answer:
Express simplifies Node.js HTTP server development through routing and middleware. Each request passes through a middleware chain until a response is sent.

--------------------------------------------------------------------
2. REQUEST AND RESPONSE

req:
"The request object represents the incoming HTTP request from the client to the server. It contains information such as request parameters, query parameters, request body, headers, HTTP method, and URL."

Contains request data: params, query, body, headers, cookies.

res:

"The response object represents the HTTP response that an Express application sends back to the client. It provides methods to send data, JSON responses, status codes, headers, and cookies."

Used to send response: status, json, send, cookie, redirect.

Example:
app.post("/users", (req, res) => {
  console.log(req.body);
  res.status(201).json({ success: true });
});

Use case:
Read client input and return API response.

Internal working:
Express parses request based on middleware such as express.json(). Response methods set headers and body, then end response.

Follow-up questions:
1. Difference between req.params and req.query?
2. How do you read request headers?
3. What is res.json?
4. How do you send status code?

Interview-ready answer:
req carries client request data, while res builds the server response. I use req.params for path values, req.query for filters, and req.body for JSON payload after body parsing middleware.

3. ROUTING, HTTP METHODS AND STATUS CODES

Routing:
"Routing in Express.js refers to defining how an application responds to incoming client requests based on the HTTP method and URL path. It allows us to organize API endpoints and handle different client operations."

app.get("/users", getUsers);
app.post("/users", createUser);
app.put("/users/:id", updateUser);
app.delete("/users/:id", deleteUser);

HTTP methods:
"HTTP methods define the type of operation a client wants to perform on a resource available on the server. They specify whether the client wants to retrieve, create, update, or delete a resource."

GET: read
POST: create
PUT: full update
PATCH: partial update
DELETE: remove

Status codes:
200 OK
201 Created
204 No Content
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Entity
500 Internal Server Error

Use case:
CRUD APIs, resource-based endpoints.

Internal working:
Express matches HTTP method and URL path to registered route handlers.

Follow-up questions:
1. Difference between PUT and PATCH?
2. What is idempotency?
3. Which status code for validation failure?
4. What is 401 vs 403?

Interview-ready answer:
PUT replaces a resource and should be idempotent; PATCH applies partial changes. I use 400/422 for validation issues, 401 for unauthenticated requests and 403 for insufficient permissions.

"GET is an HTTP method used to retrieve data from the server. It should not modify the server-side resource and is considered a safe and idempotent method."

app.get("/employees", (req, res) => {

    res.status(200).json({
        message: "Employees fetched successfully"
    });

});
Important: GET requests should not be used to modify server-side data.

"POST is an HTTP method used to submit data to the server, commonly for creating a new resource or triggering a server-side operation."

Important: POST is generally non-idempotent. Repeating the same request can create multiple resources unless the API implements duplicate prevention or idempotency.

app.post("/employees", (req, res) => {

    const employee = req.body;

    res.status(201).json({
        message: "Employee created successfully",
        data: employee
    });

});

"PUT is an HTTP method used to create or completely replace the state of a resource at a specific URL. It is an idempotent HTTP method."

app.put("/employees/:id", (req, res) => {

    const employeeId = req.params.id;

    const updatedEmployee = req.body;

    res.status(200).json({
        message: "Employee replaced successfully",
        id: employeeId,
        data: updatedEmployee
    });

});


"PATCH is an HTTP method used to apply partial modifications to an existing resource without replacing the entire resource."


app.patch("/employees/:id", (req, res) => {

    const employeeId = req.params.id;

    const updates = req.body;

    res.status(200).json({
        message: "Employee updated successfully",
        id: employeeId,
        updates
    });

});
Note: Actual partial-update behavior depends on the backend implementation.

"DELETE is an HTTP method used to remove a specified resource from the server."

app.delete("/employees/:id", (req, res) => {

    const employeeId = req.params.id;

    res.status(200).json({
        message: "Employee deleted successfully",
        id: employeeId
    });

});

POST /users with JSON -> req.body

2. MIDDLEWARE

Definition:
"Middleware in Express.js is a function that has access to the request object, response object, and the next middleware function in the application's request-response cycle. It is used to execute code, modify request and response objects, perform authentication, logging, validation, and handle errors."

Example:
app.use((req, res, next) => {
  console.log(req.method, req.url);
  next();
});

Use case:
Authentication, validation, logging, CORS, rate limiting, error handling.

Internal working:
Middleware executes in registration order. Calling next passes control to next middleware. If next(error) is called, Express skips normal middleware and goes to error middleware.

Follow-up questions:
1. What happens if next is not called?
2. Difference between app.use and app.get middleware?
3. How many middleware can a route have?
4. What is middleware chain?

Interview-ready answer:
Middleware processes requests in order. Every middleware must either call next, end response, or pass an error; otherwise request hangs.
Complete Middleware Types Comparison
Type	Registered Using	Example
Application-level	app.use()	Global logger
Router-level	router.use()	Admin authentication
Built-in	Express functions	express.json()
Third-party	External npm packages	cors, helmet
Error-handling	Four arguments	(err, req, res, next)


"Express executes middleware functions in the order in which they are registered. Each middleware can either modify the request or response, send a response, or pass control to the next middleware using next()."
--------------------------------------------------------------------
3. ERROR MIDDLEWARE
"Error-handling middleware is a special Express middleware used to centrally handle application errors. It has four parameters: err, req, res, and next. Express identifies it by its four-argument signature."

Example:
app.use((err, req, res, next) => {
  console.error(err);
  res.status(err.statusCode || 500).json({
    success: false,
    message: err.message || "Internal Server Error"
  });
});

Use case:
Centralized error responses, hiding internal errors from clients.

Internal working:
Express identifies error middleware by four parameters. next(err) routes error to this handler.

Follow-up questions:
1. Why does error middleware need four arguments?
2. How do you handle async errors?
3. What is global error handler?
4. Should you expose stack trace in production?

Interview-ready answer:
I use a centralized error middleware with four arguments. Async route errors are forwarded using next(error) or asyncHandler, and production responses should not expose stack traces.

4. MVC AND LAYERED ARCHITECTURE

MVC:
"MVC stands for Model-View-Controller. It is a software architectural pattern that separates an application into three components: Model handles data and business-related logic, View handles the user interface, and Controller handles incoming requests and coordinates between the Model and View."

Model: data/database logic
View: response/UI
Controller: request handling

Layered architecture:
"Layered architecture is a software design approach that divides an application into multiple layers, with each layer responsible for a specific task. It improves separation of concerns, maintainability, scalability and testability."

Route -> Controller -> Service -> Repository -> Database
Common layers in a MERN backend
Layer	Responsibility
Routes	Define API endpoints
Middleware	Authentication, authorization, validation
Controller	Handle request and response
Service	Business logic
Repository	Database access
Model	MongoDB schema and model
Database	Store actual data

Example:
routes/user.routes.js
controllers/user.controller.js
services/user.service.js
repositories/user.repository.js

Use case:
Maintainable backend, separation of concerns, testability.

Internal working:
Controller validates input and calls service. Service contains business logic. Repository handles DB queries. This avoids fat controllers.

Follow-up questions:
1. Why avoid business logic in controllers?
2. What is repository pattern?
3. What is DTO?
4. How do you structure large Express app?

Interview-ready answer:
I follow a layered structure: routes define endpoints, controllers handle HTTP, services contain business rules, and repositories handle database access. This improves testability and maintainability.

Repository pattern :

Repository Pattern is a design pattern that separates database logic from business logic. It acts as a middle layer between the application and the database.

// userRepository.js
class UserRepository {
  async findAll() {
    return await User.find();
  }

  async findById(id) {
    return await User.findById(id);
  }

  async create(data) {
    return await User.create(data);
  }

  async update(id, data) {
    return await User.findByIdAndUpdate(id, data, { new: true });
  }

  async delete(id) {
    return await User.findByIdAndDelete(id);
  }
}

module.exports = new UserRepository();

controller

A controller is a function that handles incoming HTTP requests, processes the request data, interacts with the required services or models, and sends an appropriate HTTP response to the client.

const userRepository = require("./userRepository");

app.get("/users", async (req, res) => {
  const users = await userRepository.findAll();
  res.json(users);
});


DTO (Data Transfer Object)

A Data Transfer Object (DTO) is an object used to transfer specific data between different layers of an application. It controls which fields are accepted or returned, without exposing the complete internal data structure.

// userDTO.js
function toUserDTO(user) {
  return {
    id: user._id,
    name: user.name,
    email: user.email
  };
}

module.exports = toUserDTO;

const toUserDTO = require("./userDTO");

app.get("/users/:id", async (req, res) => {
  const user = await userRepository.findById(req.params.id);

  res.json(toUserDTO(user));
});

Validation :

Validation is the process of checking whether the incoming data is correct and complete before saving it to the database.

const { body, validationResult } = require("express-validator");

app.post(
  "/users",
  body("name").notEmpty().withMessage("Name is required"),
  body("email").isEmail().withMessage("Valid email is required"),
  body("password").isLength({ min: 6 }).withMessage("Password must be at least 6 characters"),

  (req, res) => {
    const errors = validationResult(req);

    if (!errors.isEmpty()) {
      return res.status(400).json({ errors: errors.array() });
    }

    res.json({ message: "User created successfully" });
  }
);

Service Layer:
A Service Layer is an architectural layer that contains business logic and separates business operations from HTTP request-response handling in controllers.

service.js
const Employee = require("../models/Employee");

const createEmployee = async (data) => {

  // Check duplicate email
  const existingEmployee = await Employee.findOne({
    email: data.email
  });

  if (existingEmployee) {
    throw new Error("Employee already exists");
  }

  // Business validation
  if (data.salary < 0) {
    throw new Error("Salary cannot be negative");
  }

  // Create employee
  const employee = await Employee.create(data);

  return employee;
};

module.exports = {
  createEmployee
};

controller.js
const employeeService = require("../services/employeeService");

const createEmployee = async (req, res) => {
  try {

    const employee = await employeeService.createEmployee(
      req.body
    );

    res.status(201).json({
      success: true,
      data: employee
    });

  } catch (error) {

    res.status(400).json({
      success: false,
      message: error.message
    });

  }
};

module.exports = {
  createEmployee
};

5. REST PRINCIPLES, VERSIONING, PAGINATION AND FILTERING
REST:
"REST (Representational State Transfer) is an architectural style used for designing network-based applications. It defines a set of principles for communication between clients and servers using standard HTTP methods and resource-based URLs."

REST principles:
- Resource-based URLs.
- Proper HTTP methods.
- Stateless requests.
- Proper status codes.
- JSON representation.

All 6 REST principles
Client-Server: React handles the frontend and Express handles backend APIs.
Statelessness: We use JWT authentication, and clients send the token with each protected request.
Cacheability: We cache suitable frequently accessed data to reduce unnecessary database calls.
Uniform Interface: We use resource-based endpoints and standard HTTP methods like GET, POST, PUT, PATCH and DELETE.
Layered System: Our application can communicate through load balancers and other intermediate layers.
Code on Demand: This is optional and is generally not required in our REST API implementation."

RESTfulAPI:
"A RESTful API is an API that follows REST architectural principles to allow clients to interact with resources using standard HTTP methods."

/api/v1/users

- Changing API behaviour.

1. AUTHENTICATION VS AUTHORIZATION

Authentication:
Technical definition: Authentication is the process of verifying the identity of a user or system.

Authorization:
Technical definition: Authorization is the process of determining what resources or actions an authenticated user is allowed to access.

In my MERN applications, I implement authentication using JWT and bcrypt. After successful login, the backend generates a JWT token. For protected APIs, authentication middleware verifies the token and identifies the user. Then authorization middleware checks the user's role or permissions before allowing access to the API."

Example:
Authentication: JWT validation.
Authorization: Only admin can delete user.

Use case:
Login systems, admin panels, role-based access.

Internal working:
Authentication usually uses credentials/token. Authorization checks user roles/permissions after identity is known.

Follow-up questions:
1. What is RBAC?
2. What is ABAC?
3. Where should authorization be enforced?
4. What is least privilege?

Interview-ready answer:
Authentication identifies the user; authorization decides access. I enforce authorization on backend for every sensitive operation, never relying only on frontend checks.

2. JWT, ACCESS AND REFRESH TOKENS

JWT:
JSON Web Token containing header, payload and signature.
Technical definition: JWT (JSON Web Token) is a compact, URL-safe token format used to securely transmit claims between parties. In authentication systems, it is commonly used to represent an authenticated user's identity and related claims.

JWT helps us:
- Identify authenticated users.
- Protect APIs.
- Avoid sending email and password on every request.
- Support stateless authentication

JWT contains three parts:
Header,Payload,Signature

1. Header
Contains token type and signing algorithm.
{
  "alg": "HS256",
  "typ": "JWT"
}

2. Payload
Contains claims about the user.
{
  "userId": "USER101",
  "role": "admin"
}

3. Signature
Used to verify that the token was signed using the expected secret or private key and has not been modified.


Important interview point: JWT payload is encoded, not encrypted. Don't store passwords, bank details or other secrets inside JWT payload.

Access token:
Definition: An access token is a short-lived credential used to access protected APIs.

Refresh token:
Definition: A refresh token is a longer-lived credential used to obtain a new access token after the existing access token expires.

Refresh token rotation is a security mechanism in which a new refresh token is issued every time an existing refresh token is successfully used. The previous refresh token is invalidated.

Example:
Authorization: Bearer <accessToken>

Use case:
Stateless authentication for APIs and mobile clients.

Internal working:
Server signs JWT using secret or private key. Client sends token; server verifies signature and expiry. Refresh tokens should be stored securely and rotated on reuse.


Follow-up questions:
1. Where should JWT be stored?
2. Access token vs refresh token?
3. What is token rotation?
4. Can JWT be revoked easily?

Interview-ready answer:
I use short-lived access tokens and secure HTTP-only refresh tokens with rotation. JWTs are stateless, so revocation requires a denylist, short expiry or session/version tracking.
