DAY 1: TYPESCRIPT CORE TYPES
====================================================================

1. TYPESCRIPT VS JAVASCRIPT

Definition:
TypeScript is a strongly typed superset of JavaScript developed by Microsoft. It adds static types, interfaces, generics and compile-time error checking to JavaScript.

Example:
let userId: number = 101;
let userName: string = "Ravi";
let isActive: boolean = true;

Use case:
Large MERN applications, team projects, reusable libraries, API contracts, reducing runtime bugs.

Internal working:
TypeScript code is not executed directly by browsers or Node.js. The TypeScript compiler, tsc, or a bundler such as Vite/Webpack with ts-loader/esbuild converts TypeScript into JavaScript. Type annotations are removed during compilation because JavaScript does not understand them at runtime.

Follow-up questions:
1. Is TypeScript statically or dynamically typed?
2. Does TypeScript improve runtime performance?
3. What is transpilation?
4. Can TypeScript catch all bugs?

Interview-ready answer:
TypeScript adds compile-time type safety to JavaScript. It catches many errors before runtime, improves maintainability and developer experience, but it compiles down to JavaScript and does not inherently make runtime faster.

--------------------------------------------------------------------
2. TYPE INFERENCE

Definition:
Type inference means TypeScript automatically detects the type of a variable based on its assigned value.

Example:
let count = 10;          // inferred as number
let name = "Ravi";       // inferred as string
let items = [];          // inferred as any[] if not typed

Use case:
Reduce unnecessary type annotations while keeping type safety.

Internal working:
During type checking, TypeScript analyzes the initializer and assigns the best matching type. Once inferred, incompatible assignments cause compile-time errors.

Follow-up questions:
1. When should we explicitly define types?
2. What is the type of an empty array?
3. What is implicit any?

Interview-ready answer:
TypeScript infers types from initial values. I rely on inference for simple local variables but explicitly type function parameters, API responses, component props and shared utilities.

--------------------------------------------------------------------
3. PRIMITIVE TYPES, ARRAYS, TUPLES AND OBJECT TYPES

Primitive types:
string, number, boolean, null, undefined, symbol, bigint.

Array types:
let ids: number[] = [1, 2, 3];
let users: string[] = ["A", "B"];
let values: Array<number> = [1, 2];

Tuple:
A tuple is an array with fixed length and fixed types at specific positions.

let user: [string, number] = ["Ravi", 25];

Object type:
let user: { id: number; name: string; email?: string } = {
  id: 1,
  name: "Ravi"
};

Use case:
Arrays for lists, tuples for fixed structures like coordinates or key-value pairs, object types for entity shapes.

Internal working:
TypeScript checks assignments and property access against declared shapes at compile time. Optional properties may be undefined.

Follow-up questions:
1. Difference between array and tuple?
2. What does ? mean in object type?
3. How do you define readonly array?
4. What is the difference between number[] and Array<number>?

Interview-ready answer:
Arrays allow variable length with a consistent element type, while tuples define fixed length and position-based types. I use object types or interfaces to describe entity structures such as users, products and API responses.

--------------------------------------------------------------------
4. ANY VS UNKNOWN; NEVER VS VOID

any:
any is a TypeScript type that disables static type checking. 
A value of type any can be assigned to any other type, and any other type can be assigned to it.

let value: any = "hello";

value = 10;
value = true;
value.toUpperCase();
value.foo.bar();

Use Cases
  Legacy JavaScript migration
  Quick prototyping
  Third-party libraries without types
  Temporary dynamic data


unknown:

unknown is a type-safe alternative to any. 
It accepts any value, but the value must be narrowed or validated before it can be used.

let data: unknown = "hello";

data.toUpperCase(); // Error

if (typeof data === "string") {
  data.toUpperCase(); // OK
}

Use Cases
  API responses
  JSON parsing
  External data
  User input
  Third-party library data

never:
never is a TypeScript type that represents a value that can never occur. 
It is used for functions that never return normally, such as functions that always throw errors or run infinite loops.


function handleError(): never {
  throw new Error("Failed");
}

Use Cases
  Error functions
  Infinite loops
  Exhaustive checks
  Unreachable code

void:
void is a TypeScript type that represents the absence of a meaningful return value. 
It is used for functions that do not return a value.

function logMessage(): void {
  console.log("Done");
}

Use Cases
Logging functions
Event handlers
Side-effect functions


Internal working:
TypeScript allows any operations on any, but unknown requires type narrowing. never helps TypeScript prove that all cases in a union are handled.

Follow-up questions:
1. Why is unknown better than any?
2. When do we use never?
3. Difference between void and undefined?
4. How do you narrow unknown?

Interview-ready answer:
I avoid any because it disables type safety. I use unknown for uncertain external data and narrow it using typeof, instanceof or validation. void means no meaningful return value, while never means a value can never occur.



--------------------------------------------------------------------
5. TYPE ALIASES VS INTERFACES

Type alias:

A type alias is a name given to any TypeScript type.
It can represent primitives, unions, intersections, tuples, functions, and object types.

type UserID = string | number;

type User = {
  id: number;
  name: string;
};

const user: User = {
  id: 1,
  name: "Ravi"
};

Use Cases
  Primitive types
  Union types
  Intersection types
  Function types
  Tuples
  Complex types


interface:
An interface is a TypeScript structure that describes the shape of an object. 
It is mainly used for object types and can be extended or implemented.

interface User {
  id: number;
  name: string;
}

Example:
type Status = "active" | "inactive";

interface Admin extends User {
  role: string;
}

Use Cases
  Object shapes
  Class contracts
  Extending types
  Implementing types

Use case:
Use type for unions, utility types, tuples and complex types. Use interface for object contracts, especially when extension or declaration merging is needed.

Internal working:
Interfaces create named object contracts and support declaration merging. Type aliases can represent more kinds of types but cannot be merged after declaration.

Follow-up questions:
1. Can interface extend type alias?
2. What is declaration merging?
3. Which one should we use in React props?
4. Can type alias represent union types?

Interview-ready answer:
Interfaces are best for object shapes and extension, while type aliases are more flexible for unions, primitives, tuples and utility-based types. In modern projects, either is acceptable for props, but consistency matters most.

--------------------------------------------------------------------
6. UNION, INTERSECTION AND LITERAL TYPES


Union type:
A union type allows a value to be one of several types. 
It is created using the pipe symbol ( | ).

let id: string | number;

Use Cases
  API responses
  Function parameters
  Conditional types
  Multiple possible values

Intersection type:
An intersection type combines multiple types into one. 
It is created using the ampersand symbol ( & ).

type A = { name: string };
type B = { age: number };

type Person = A & B;

const person: Person = {
  name: "Ravi",
  age: 25
}
Use Cases
  Combining types
  Reusing types
  Building complex types
  Mixins

Literal type:
A literal type is a type that represents a specific value instead of a general type.

let direction: "up" | "down";
  direction = "up";
  direction = "down";

Use Cases
  Fixed set of values
  API status codes
  Config options
  Function parameters

Internal working:
Union allows assignment if value matches at least one member. Intersection requires value to satisfy all combined types.

Follow-up questions:
1. Difference between union and intersection?
2. How do you narrow a union?
3. What is a literal type?
4. What is discriminated union?

Interview-ready answer:
Unions allow one of multiple types, intersections combine requirements from multiple types, and literal types restrict values to specific allowed options. I use discriminated unions for predictable state handling.

7. ENUMS, OPTIONAL AND READONLY PROPERTIES

Enum:
Enums are a TypeScript feature that defines a set of named constants.
 They make code more readable and maintainable.

enum Role {
  Admin = "ADMIN",
  User = "USER"
}

let role: Role = Role.Admin;

Use Cases
  Fixed set of values
  User roles
  API status
  Config options


Optional property:
Optional properties are properties that may or may not be present in an object. 
They are defined using a question mark (?).

interface User {
  id: number;
  name: string;
  email?: string;
}

const user1: User = {
  id: 1,
  name: "Ravi"
};

const user2: User = {
  id: 2,
  name: "Sita",
  email: "sita@mail.com"
};

Use Cases
  API responses
  Config objects
  Partial data
  Optional fields

Readonly property:
Readonly properties are properties that cannot be modified after initialization.
 They are defined using the readonly keyword.

interface User {
  readonly id: number;
  name: string;
}

const user: User = {
  id: 1,
  name: "Ravi"
};

user.id = 2; // Error

Use Cases
  Immutable data
  Config objects
  Constants
  Preventing accidental changes

Internal working:
String enums compile to JavaScript objects. Optional properties add undefined to their type. readonly is compile-time only; it does not freeze objects at runtime.

Follow-up questions:
1. String enum vs numeric enum?
2. Is readonly immutable at runtime?
3. Enum vs union of string literals?
4. What is const enum?

Interview-ready answer:
I usually prefer string literal unions over enums in modern TypeScript because they are simpler and produce less runtime code. readonly prevents reassignment at compile time but does not deeply freeze objects.

8. FUNCTION TYPES, OVERLOADS AND TYPE ASSERTIONS

Function type:
Technical definition: A function type describes the parameter types and return type of a function, so TypeScript can check every call and every implementation against it.

// 1. Type alias
type Add = (a: number, b: number) => number;
const add: Add = (a, b) => a + b;     // a, b types inferred from Add

// 2. Interface with call signature
interface Add2 {
  (a: number, b: number): number;
}

// 3. Inline
function run(cb: (err: Error | null, data?: string) => void) {}

Overloads:
Technical definition: Overloads let you declare multiple call signatures for one function. They are a compile-time feature. At runtime there is only one implementation, and it must be compatible with all overload signatures.

function format(value: string): string;       // overload signature 1
function format(value: number): string;       // overload signature 2
function format(value: string | number): string {   // implementation signature
  return typeof value === "string" ? value.trim() : value.toFixed(2);
}

format("a");     // OK
format(5);       // OK
format(true);    // Error: no overload matches

Type assertion:
Technical definition: A type assertion tells the compiler to treat a value as a specific type, overriding its inferred type. It is erased at compile time and produces no runtime code, no checking, no conversion.

const input = document.getElementById("email") as HTMLInputElement;

Use case:
Function types for callbacks, overloads for flexible APIs, assertions for DOM elements or external library values.

Internal working:
Overloads provide multiple call signatures, but only one implementation exists. Type assertions do not convert data at runtime; they only affect compile-time checking.

Follow-up questions:
1. Difference between type assertion and type conversion?
2. When should overloads be used?
3. What is as unknown as T?
4. Why is type assertion risky?

Interview-ready answer:
Type assertions change compile-time assumptions, not actual runtime data. I use them sparingly, especially for DOM or third-party values, and prefer validation or type guards when data comes from external sources.

DAY 2: TYPE NARROWING AND ADVANCED TYPES
====================================================================

1. TYPE NARROWING AND TYPE GUARDS

Definition:
Type narrowing is the process of reducing a broad type to a more specific type based on checks.

Example:
function printId(id: string | number) {
  if (typeof id === "string") {
    console.log(id.toUpperCase());
  } else {
    console.log(id.toFixed(2));
  }
}

Type guards:
typeof, instanceof, in, custom type guards.

function isUser(value: unknown): value is User {
  return typeof value === "object" && value !== null && "id" in value;
}

Use case:
API responses, event handling, union types, error handling.

Internal working:
TypeScript control-flow analysis tracks checks inside conditions. After a check, it narrows the possible type within that branch.

Follow-up questions:
1. What is a type predicate?
2. Difference between typeof and instanceof?
3. How do you validate API response types?
4. What is exhaustive checking?

Interview-ready answer:
I narrow union types using typeof, instanceof, in checks or custom type guards. For API data, compile-time types alone are not enough, so I use runtime validation such as Zod before trusting the response.

--------------------------------------------------------------------
2. DISCRIMINATED UNIONS

Definition:
A discriminated union is a union of object types sharing a common literal property called discriminator.

Example:
type RequestState =
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "error"; message: string };

function render(state: RequestState) {
  switch (state.status) {
    case "loading":
      return "Loading...";
    case "success":
      return state.data;
    case "error":
      return state.message;
  }
}

Use case:
API request states, form states, Redux async states, modal states.

Internal working:
The literal discriminator allows TypeScript to narrow the object shape inside each case. If a new state is added, exhaustive switch handling can produce compile-time safety.

Follow-up questions:
1. Why are discriminated unions useful?
2. How do they differ from normal unions?
3. How do you ensure all cases are handled?

Interview-ready answer:
Discriminated unions model mutually exclusive states clearly. I use a common literal field such as status or type, then switch on it to get precise type narrowing and safer state handling.

--------------------------------------------------------------------
3. GENERICS AND GENERIC CONSTRAINTS

Definition:
Generics allow functions, interfaces and components to work with multiple types while preserving type safety.

Example:
function firstItem<T>(items: T[]): T | undefined {
  return items[0];
}

Generic constraint:
function getProperty<T, K extends keyof T>(obj: T, key: K) {
  return obj[key];
}

Use case:
Reusable API functions, generic components, utility functions, typed hooks.

Internal working:
TypeScript replaces T with the actual type at call time and checks operations allowed by the constraint.

Follow-up questions:
1. What is a generic constraint?
2. What is default generic type?
3. Why are generics better than any?
4. How do you type a generic React component?

Interview-ready answer:
Generics provide reusable type-safe abstractions. Instead of any, I use type parameters with constraints so TypeScript can validate both input and output types.

4. keyof, typeof AND INDEXED ACCESS TYPES

keyof:
Creates union of keys of an object type.

type User = { id: number; name: string };
type UserKeys = keyof User; // "id" | "name"

typeof:
Gets type of a variable or function.

const config = { apiUrl: "/api", timeout: 5000 };
type Config = typeof config;

Indexed access:
Gets type of a specific property.

type UserName = User["name"]; // string

Use case:
Safe property access, configuration typing, dynamic keys, Redux state slices.

Internal working:
These are type-level operators evaluated during compilation, not runtime.

Follow-up questions:
1. Difference between keyof and typeof?
2. What is indexed access type?
3. How do you safely access dynamic object keys?

Interview-ready answer:
keyof extracts object keys as a union, typeof extracts a value's type, and indexed access extracts a property type. They help build reusable and type-safe utilities.

--------------------------------------------------------------------
5. infer AND CONDITIONAL TYPES

Conditional type:
Chooses type based on a condition.

type IsString<T> = T extends string ? true : false;

infer:
Infers a type inside a conditional type.

type ElementType<T> = T extends Array<infer U> ? U : never;

Example:
type Numbers = ElementType<number[]>; // number

Use case:
Utility types, extracting promise values, array item types, function return types.

Internal working:
Conditional types are evaluated by TypeScript's type system. infer captures a nested type during pattern matching.

Follow-up questions:
1. What does infer do?
2. What is distributive conditional type?
3. How is ReturnType implemented?

Interview-ready answer:
Conditional types choose types based on whether one type extends another. infer captures nested types, enabling utilities such as extracting array item types or Promise resolution types.

--------------------------------------------------------------------
6. MAPPED AND TEMPLATE LITERAL TYPES

Mapped type:
Creates new type by transforming each property of existing type.

type OptionalUser = {
  [K in keyof User]?: User[K];
};

Template literal type:
Creates string-based types using template syntax.

type Route = `/api/${string}`;

Use case:
Form state, API route types, event handler maps, dynamic object keys.

Internal working:
Mapped types iterate over keys using keyof and transform value types. Template literal types combine string literals and types at compile time.

Follow-up questions:
1. What is Partial implementation?
2. What are key remapping types?
3. How are template literal types useful?

Interview-ready answer:
Mapped types transform existing object types property by property, while template literal types create precise string patterns. They are useful for typed routes, event names and form fields.

Interview-ready answer:
Utility types help derive types instead of duplicating them. I commonly use Partial for update payloads, Pick/Omit for API contracts, Record for maps, and Awaited/ReturnType for async service functions.

4. RUNTIME VALIDATION VS COMPILE-TIME TYPES

Compile-time types:
TypeScript checks code during development/build.

Runtime validation:
Validates actual incoming data while application is running.

Example with Zod:
const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.string().email()
});

QUICK REVISION: MOST ASKED TYPESCRIPT ANSWERS
====================================================================

1. TypeScript adds static typing to JavaScript and compiles to JavaScript.
2. Type inference reduces explicit annotations but explicit types improve clarity at boundaries.
3. unknown is safer than any because it requires narrowing.
4. never represents impossible values; void represents no meaningful return.
5. Interfaces describe object contracts; type aliases support unions and complex types.
6. Discriminated unions model mutually exclusive states safely.
7. Generics create reusable type-safe functions and components.
8. keyof, typeof and indexed access types build advanced reusable types.
9. Utility types such as Partial, Pick, Omit and Record reduce duplication.
10. TypeScript types are erased at runtime; API data needs runtime validation.
11. React props and children are typed using interfaces and ReactNode.
12. Axios generics type response data but do not validate actual backend response.
13. Zod validates runtime data and can infer TypeScript types.
14. strict, strictNullChecks and noImplicitAny improve code reliability.
15. Migrate JavaScript to TypeScript incrementally, starting with shared types and API boundaries.
