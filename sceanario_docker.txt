A1. Deploy a MERN app on EC2 from scratch. Steps cheppandi.
--------------------------------------------------------------
SAMPLE ANSWER
1. EC2 launch: Ubuntu, t3.small, key pair, Security Group (22 from my
   IP, 80, 443).
2. SSH: ssh -i key.pem ubuntu@<ip>
3. Install: Node 20, Nginx, Git, PM2.
4. Backend: git clone, npm ci --omit=dev, create .env, pm2 start
   server.js --name api, pm2 startup, pm2 save.
5. Frontend: npm run build, copy build to /var/www/ritzzy/build (or
   build locally and scp).
6. Nginx: serve build, proxy /api and /socket.io to localhost:5000.
7. Domain: Route 53 A record to Elastic IP.
8. SSL: sudo certbot --nginx -d admin.example.com
9. Verify: curl https://admin.example.com/api/health

COMMANDS
sudo apt update && sudo apt install -y nginx git
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs
npm install -g pm2
git clone <repo> && cd <repo> && npm ci --omit=dev
pm2 start server.js --name api && pm2 startup && pm2 save
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d admin.example.com

A3. Nginx "502 Bad Gateway" vastundi. Reason enti?
--------------------------------------------------------------
SAMPLE ANSWER
502 ante Nginx upstream (Node app) ni reach cheyaledu.
Causes:
  - Node app crash ayindi / run avvatledu
  - Wrong port in proxy_pass
  - App different port lo run avtundi

Debug:
  pm2 list
  pm2 logs api
  curl http://localhost:5000/health
  grep proxy_pass /etc/nginx/sites-enabled/*

Fix: app restart (pm2 restart api), port correct cheyadam, crash
reason logs lo chusi fix cheyadam.
Prevention: pm2 startup save, health check alerts.

Related codes:
  504 Gateway Timeout : app respond cheyadaniki chala time
                        (proxy_read_timeout penchali, or slow API fix)
  413 Request Entity Too Large : client_max_body_size 20M; set cheyali

A5. EC2 disk full ayindi, app crash avtundi. Ela fix chestaru?
--------------------------------------------------------------
SAMPLE ANSWER
1. Confirm:
     df -h
2. Peddha folders find:
     sudo du -h --max-depth=1 / 2>/dev/null | sort -hr | head -10
     sudo du -h --max-depth=1 /var | sort -hr | head
3. Common culprits and cleanup:
     - Logs:  sudo journalctl --vacuum-size=200M
              pm2 flush
              sudo truncate -s 0 /var/log/nginx/access.log
     - Docker: docker system prune -a
     - Old builds, node_modules, uploads
     - apt cache: sudo apt clean
4. Permanent fix:
     - logrotate configure
     - EBS volume size penchadam:
         aws ec2 modify-volume --volume-id vol-0abc --size 50
         sudo growpart /dev/xvda 1
         sudo resize2fs /dev/xvda1
     - Uploads S3 ki move
     - CloudWatch alarm disk usage meeda

A6. Server CPU 100% ayindi. Em chestaru?
--------------------------------------------------------------
SAMPLE ANSWER
1. Identify: top / htop (which process)
2. Node process ayithe: pm2 monit, pm2 logs
3. Reasons: infinite loop, heavy sync operation, unindexed MongoDB
   query, traffic spike
4. Quick relief: pm2 restart api
5. Fix:
     - Slow query find (MongoDB profiler, explain), index add
     - Heavy work ni background job / queue ki move
     - PM2 cluster mode: pm2 start server.js -i max
     - Scale out: ALB + Auto Scaling Group
6. Prevention: CloudWatch CPU alarm (80% for 10 min)

A7. React app ni S3 + CloudFront lo host chesam. Refresh chesthe
    404/403 vastundi. Enduku? Fix?
--------------------------------------------------------------
SAMPLE ANSWER
Reason: React Router client-side routing. /dashboard refresh chesthe
CloudFront/S3 lo aa file ledu, anduke 403/404.

Fix: CloudFront Custom Error Responses:
  403 -> /index.html -> response code 200
  404 -> /index.html -> response code 200

Also: kotha build upload chesaka cache clear:
  aws s3 sync ./build s3://ritzzy-admin-web --delete
  aws cloudfront create-invalidation --distribution-id E1ABC --paths "/*"

Best practice: hashed JS/CSS files ki long cache, index.html ki short
cache.


--------------------------------------------------------------
A8. EC2 nundi S3 upload chesthe "AccessDenied" vastundi.
--------------------------------------------------------------
SAMPLE ANSWER
Check order:
  1. EC2 ki IAM role attach ayyinda? (Instance profile)
  2. Role policy lo s3:PutObject action and correct bucket ARN
     (arn:aws:s3:::bucket/* for objects) undha?
  3. Bucket policy lo explicit deny undha?
  4. Region / bucket name correct?
  5. Server lo identity check:
       aws sts get-caller-identity

Fix: policy update:
{
  "Effect": "Allow",
  "Action": ["s3:PutObject", "s3:GetObject"],
  "Resource": "arn:aws:s3:::ritzzy-uploads/*"
}
Access keys code lo pettakudadu, IAM role vadali.

A9. Socket.io / WebSocket connection tarachu disconnect avtundi
    (Nginx / ALB venuka). Fix?
--------------------------------------------------------------
SAMPLE ANSWER
Nginx:
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  proxy_read_timeout 3600s;       # idle timeout penchadam
  proxy_send_timeout 3600s;

ALB:
  - Idle timeout penchali (default 60 sec)
  - Multiple instances unte sticky sessions enable cheyali
  - Socket.io multiple servers lo Redis adapter vadali
Client side: heartbeat/ping, auto reconnect enable.

crontab -e
0 2 * * * /home/ubuntu/backup.sh >> /var/log/backup.log 2>&1

K1. LIVE TASK: Node app ni Kubernetes lo deploy cheyandi.
--------------------------------------------------------------
SAMPLE ANSWER
1. Image push:
     docker build -t sathish/ritzzy-api:1.0 .
     docker push sathish/ritzzy-api:1.0
2. Secret:
     kubectl create secret generic db-secret \
       --from-literal=uri='mongodb://mongo:27017/ritzzy'
3. deployment.yaml:
     apiVersion: apps/v1
     kind: Deployment
     metadata:
       name: api
     spec:
       replicas: 3
       selector:
         matchLabels:
           app: api
       template:
         metadata:
           labels:
             app: api
         spec:
           containers:
             - name: api
               image: sathish/ritzzy-api:1.0
               ports:
                 - containerPort: 5000
               env:
                 - name: MONGO_URI
                   valueFrom:
                     secretKeyRef:
                       name: db-secret
                       key: uri
               readinessProbe:
                 httpGet:
                   path: /health
                   port: 5000
               resources:
                 requests:
                   cpu: "100m"
                   memory: "128Mi"
                 limits:
                   cpu: "500m"
                   memory: "256Mi"
4. service.yaml:
     apiVersion: v1
     kind: Service
     metadata:
       name: api-service
     spec:
       type: NodePort
       selector:
         app: api
       ports:
         - port: 80
           targetPort: 5000
5. Apply and verify:
     kubectl apply -f deployment.yaml -f service.yaml
     kubectl get pods
     kubectl get svc
     minikube service api-service --url

  console.log("SIGTERM received, closing server");
  server.close(async () => {
    await mongoose.connection.close();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10000);   // force exit
});

Docker stop and Kubernetes pod termination SIGTERM pamputayi, so
ee handler zero downtime ki important.
